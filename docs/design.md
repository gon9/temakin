- ステータス: ドラフト
- 最終更新: 2026-07-04

## 1. 全体アーキテクチャ

サーバーレスの完全クライアントサイドSPA。1台のスマホを回して遊ぶ「ホットシート」方式のため、通信・同期の仕組みは持たない。

```
┌─────────────────────────────────────────────┐
│  ブラウザ (iOS Safari / Android Chrome)      │
│                                             │
│  ┌───────────┐  ┌────────────┐  ┌────────┐  │
│  │ UI層       │  │ ゲームロジック│  │ Vision層 │  │
│  │ 画面遷移    │←→│ バトルエンジン │←→│ 撮影     │  │
│  │ バトル演出  │  │ ステータス生成│  │ 顔切り抜き│  │
│  │ (Canvas)  │  │ セッション状態│  │ 特徴量抽出│  │
│  └───────────┘  └────────────┘  └────────┘  │
│         すべての画像・状態は端末内のみ          │
└─────────────────────────────────────────────┘
```

### 技術スタック

| レイヤ | 技術 | 選定理由 |
|---|---|---|
| 言語/ビルド | TypeScript + Vite | 標準的。PWAプラグインでオフライン化が容易 |
| UIフレームワーク | Svelte（または軽量なReact） | バンドルを小さく保ち初回ロードを速くする |
| 描画 | Canvas 2D（バトル演出） | WebGL必須の表現は不要。2Dで十分派手にできる |
| カメラ | `getUserMedia` + `<video>` → Canvasキャプチャ | 標準API。外カメ/インカメは `facingMode` で切替 |
| 顔切り抜き | MediaPipe Tasks Vision(Selfie Segmentation + Face Detector) | WASM製・端末内で完結。実績が多い |
| 特徴量抽出 | 自前実装（Canvas ピクセル解析） | 依存を増やさない。要件が単純（色・面積・輪郭） |
| 永続化 | メモリのみ（セッション状態）。設定は `localStorage` | プライバシー要件（画像を残さない）に合わせる |
| PWA | vite-plugin-pwa (Workbox) | 初回ロード後オフライン動作 |

## 2. 画面フローと状態遷移

```
[タイトル]
   ↓ はじめる
[プレイヤー登録] ←──────────┐（プレイヤー追加）
   │ 名前入力 → 顔撮影(インカメ/スキップ)
   ↓ 全員登録完了(2〜8人)
[ラウンド開始] … 対戦カード発表（トーナメント編成）
   ↓
[巻きタイム] … 「手巻きを作ってね」画面。できた人からスキャンへ
   ↓
[スキャン] … 外カメで撮影 → プレビュー → 確定
   ↓（対戦者2人分そろったら）
[ファイター生成演出] … ステータス・二つ名をドロールのように発表
   ↓
[バトル] … オートバトル演出(30〜60秒)
   ↓
[リザルト] … 勝者表彰・シェア画像生成
   ↓ 次のラウンドへ / 終了
[総合結果] … 本日の手巻き王の表彰
```

セッション状態は単一のステートマシンで管理する。ブラウザリロードで状態が消えることは許容する（1プレイが短いため）。

## 3. データモデル

```typescript
type Player = {
  id: string;
  name: string;
  /** 背景除去済みの顔画像。未撮影なら null → デフォルトアバター */
  faceImage: ImageBitmap | null;
  wins: number;
};

type FighterStats = {
  hp: number;        // 100〜300
  attack: number;    // 10〜50
  defense: number;   // 0〜30
  speed: number;     // 10〜50
  luck: number;      // 会心・回避率に寄与 0〜20
};

type Fighter = {
  playerId: string;
  photo: ImageBitmap;        // スキャンした手巻きの切り抜き
  stats: FighterStats;
  title: string;             // 二つ名 例:「はみ出し狂戦士」
  moves: Move[];             // 1〜4個。色クラスタ数で決まる
  features: TemakiFeatures;  // デバッグ・演出用に生特徴量も保持
};

type Move = {
  name: string;              // 例:「紅きマグロ斬り」
  power: number;
  accuracy: number;          // 0.7〜1.0
  element: 'red' | 'green' | 'yellow' | 'white' | 'dark';
};

type TemakiFeatures = {
  areaRatio: number;      // 画面に占める手巻き面積の割合 0..1
  redness: number;        // 赤系ピクセルの強度 0..1
  brightness: number;     // 平均明度 0..1
  glossiness: number;     // ハイライト(高輝度画素)率 0..1
  contourRuggedness: number; // 輪郭の凸凹度(はみ出し度) 0..1
  colorClusters: ColorCluster[]; // 主要色クラスタ(最大6)
};
```

## 4. Vision層の設計

### 4.1 手巻き領域の抽出

食卓の背景（皿・テーブル）から手巻きを切り出す。ネタ識別は不要で、領域が取れれば十分。

1. 撮影ガイドの枠内を処理対象とする（ユーザーに枠内へ収めてもらうことで問題を単純化する）
2. 枠内の中央領域から前景色をサンプリングし、背景（枠の外周部の色）との色距離でセグメンテーション
3. モルフォロジー処理（収縮・膨張）でノイズ除去し、最大連結成分を手巻き領域とする
4. 領域が小さすぎる/取れない場合は「もう少し寄って撮ってね」を表示して再撮影を促す

MediaPipeの汎用セグメンテーションは人物向けのため、手巻きには上記の古典的手法を使う。**枠ガイドで撮影条件を制約するのが精度の要**。

### 4.2 特徴量抽出

手巻き領域のピクセルをHSVで解析する。

| 特徴量 | 算出方法 |
|---|---|
| `areaRatio` | 手巻き領域ピクセル数 ÷ ガイド枠内ピクセル数 |
| `redness` | 色相が赤域(±30°)かつ彩度>0.4 のピクセル比率 |
| `brightness` | V(明度)の平均 |
| `glossiness` | V>0.9 かつ S<0.3 のピクセル(ハイライト)比率 |
| `contourRuggedness` | 輪郭周長² ÷ (4π×面積) の円形度からのズレ。はみ出た具が多いほど大 |
| `colorClusters` | HS平面のk-meansクラスタリング(k=6から縮約)。占有率5%以上のクラスタを採用 |

### 4.3 顔ネタカード（プレイヤー登録時）

1. インカメ映像に MediaPipe Face Detector で顔枠ガイドを表示
2. シャッター時に Selfie Segmentation で人物マスクを取得し、顔枠で切り抜き
3. 円形にトリミングして `ImageBitmap` で保持（端末外に出さない）

## 5. ステータス生成の設計

### 5.1 変換式

特徴量→ステータスは決定的な純関数にする（テスト容易・再抽選防止）。

```
hp      = 100 + 200 × clamp(areaRatio × 2.5)
attack  = 10 + 40 × (0.7 × redness + 0.3 × contourRuggedness)
defense = 30 × (1 − contourRuggedness)         // 綺麗に巻くほど堅い
speed   = 10 + 40 × (0.5 × glossiness + 0.5 × brightness)
luck    = 20 × saturationVariance              // 彩り豊かだと運が良い
```

- 各値は 0..1 に正規化した特徴量から線形変換し、clampする
- **トレードオフが生まれることが重要**: はみ出させると攻撃↑防御↓、デカく巻くとHP↑だが（面積↑→相対的に輪郭が整い）攻撃は伸びにくい、など「全部盛り最強」にならないよう係数を調整する
- 係数はプレイテストで調整するため、1ファイル(`statFormula.ts`)に定数として隔離する

### 5.2 技の生成

- `colorClusters` の各クラスタが1つの技になる（最大4つ。占有率上位から採用）
- クラスタの色相から属性(`element`)を決め、属性×占有率で技名テーブルから技名を引く
  - 例: 赤クラスタ占有率高 →「紅きマグロ斬り」(power大)、緑 →「きゅうりの盾」(防御技)
- 技名テーブルはデータファイル(`moves.json`)で管理し、コード変更なしに増やせるようにする

### 5.3 二つ名の生成

最も突出した特徴量1〜2個の組み合わせで二つ名テーブルから決定する。
例: `contourRuggedness`最大 →「はみ出し狂戦士」、`defense`最大 →「鉄壁の海苔巻き」、全特徴量が平均的 →「バランスの求道者」。

## 6. バトルエンジンの設計

### 6.1 ルール（ターン制オートバトル）

```
1. speedが高い方が先攻。以降交互にターンを進める
2. 自ターン: 技を1つ選択(占有率を重みにランダム) → 命中判定 → ダメージ計算
3. ダメージ = 技power × (attack / (attack + defense_enemy)) × 乱数(0.85..1.15)
4. 会心(×2)確率 = 5% + luck×0.5%、回避確率 = 3% + luck_enemy×0.4%
5. HPが0になったら敗北。20ターン経過時は残HP率で判定勝ち
```

- 期待勝率がステータス合計に概ね比例しつつ、1〜2割の番狂わせが起きる係数を目標とする（シミュレーションテストで検証する）
- 乱数はシード付きPRNG（`playerId`＋ラウンド番号）にし、リプレイ再現とテストを可能にする

### 6.2 バトル演出

- ロジック（結果計算）と演出（再生）を分離する。バトル開始時に全ターンのログを一括計算し、演出層はログを順に再生するだけにする
- 演出: 手巻き実写＋顔合成のファイターが画面両端に立ち、技ごとにカットイン・画面シェイク・ダメージ数字・実況テキストを表示
- 実況テキストは技のelementと結果（会心/回避/倒した）から定型文テーブルで生成する
- 1ターン2〜3秒、スキップボタンで倍速可能

### 6.3 トーナメント編成

- 3人以上はシングルイルミネーション（勝ち抜き）。奇数人数はシード（不戦勝）を乱数で割当
- 「巻きタイム」は全員並行で行い、対戦カードの2人がスキャンを終えたらそのバトルを開始できる（待ち時間の最小化）

- `battle`: 同シードで同結果になること。1000戦シミュレーションでステータス差と勝率の関係が設計目標に収まること

## 8. 主要リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 食卓の照明で領域抽出が不安定 | ステータスが撮影条件でブレる | 枠ガイドで条件を制約。露出の目安をガイド表示。プレビューで抽出結果（輪郭線）を見せて納得感を担保 |
| 「同じ手巻きでスキャンし直すと違うステータス」問題 | ガチャ再抽選で興ざめ | スキャン確定後は撮り直し不可。特徴量→ステータスは決定的関数 |
| iOS Safariのカメラ・WASM制約 | 主要ターゲットで動かない | 開発初期からiOS実機で検証。MediaPipeはWASM(SIMD)版の動作確認を最優先タスクにする |
| ステータスバランス崩壊（必勝法の発見） | 戦略パートが死ぬ | 係数を1ファイルに隔離し、シミュレーションテストで勝率分布を常時検証 |
| 演出が長くて食事のテンポを削ぐ | 「ゲームが食事を邪魔しない」原則に反する | 1バトル60秒上限・倍速スキップを最初から実装 |
